# 교사(Claude) 상세 설명 생성 지침

기존 `work/teacher/batch_all.jsonl`의 짧은 설명은 **그대로 둔다**. 이 작업은 같은 샘플에
더 자세한 설명을 **추가로** 붙여 `work/teacher_detailed/`에 쓰는 것이다.

짧은 설명은 3~5문장이라 학생 VLM이 "무엇을 보고 그렇게 판단했는지"의 중간 과정을 배우기 어렵다.
상세 버전은 장면 묘사 → 양쪽 근거 → 히트맵 검증 → 저울질 → 결론의 순서를 전부 글로 남겨,
학생이 결론뿐 아니라 판단 과정을 따라 배우게 하는 것이 목적이다.

각 샘플마다 `distill/work/panel/{id}.jpg` 한 장을 본다. 가로로 세 칸이다.
1. original: 384×384로 통일한 원본
2. grad-cam: MobileViT v2가 "자기 판정" 쪽으로 주목한 영역. 흰 박스가 3번 크롭 위치
3. crop x3: 히트맵 최고점 주변 128px를 3배 확대한 것

배치 파일 한 줄에 주어지는 정보는 다음뿐이다.
- `mobilevit_prob_real`, `mobilevit_pred`: 분류기 확률(1에 가까울수록 실제 사진)과 판정
- `teacher_verdict`, `teacher_confidence`, `observations`: 이전 교사가 내린 판정·확신·근거

**정답 라벨은 주지 않는다.** 그리고 기존 판정을 뒤집지 않는다.

## 규칙
- `teacher_verdict`와 `teacher_confidence`는 **바꾸지 않는다.** 상세 설명이 그것과 모순되면 안 된다.
  기존 `observations`의 근거는 상세 설명 안에 녹여 쓰되, 이미지에서 새로 보이는 것은 더 보태도 된다.
- 근거는 구체적으로 쓴다. "부자연스럽다" 대신 "개의 앞다리가 몸통에 녹아 붙어 있다"처럼
  **어디에 무엇이 어떻게 보이는지**를 쓴다.
- `evidence_ai`와 `evidence_real`에 **양쪽 근거를 모두** 적는다. 한쪽이 비어 보여도 반대쪽 단서를
  한 번은 찾아보고, 정말 없으면 빈 배열로 둔다. 판정은 양쪽을 저울질한 결과여야 한다.
- 볼 만한 것: 해부학적 오류(손가락, 다리, 눈), 녹아내린 사물 경계, 뭉개진 글자, 반복 텍스처,
  조명/그림자 불일치, 비현실적으로 매끈한 표면, 워터마크·JPEG 블록·센서 노이즈 같은 촬영 흔적.
- 모든 이미지는 384 JPEG로 재인코딩됐다. **파일 형식, 해상도, 압축 품질 자체는 근거로 쓰지 않는다.**
  (저해상도 원본을 확대해 흐릿한 것도 마찬가지)
- 히트맵이 배경이나 의미 없는 곳을 가리키면 솔직하게 `no`라고 쓴다. 발표의 핵심 검증 포인트다.
- 지어내지 않는다. 안 보이는 것은 "안 보인다"고 쓴다. `teacher_confidence`가 low면
  상세 설명도 유보적인 어조를 유지한다.
- 한국어. 일반인이 이해할 말로.

## 출력 형식 (한 줄에 JSON 하나, JSONL)
```json
{"id": "tg0000",
 "scene": "이미지에 무엇이 찍혀 있는지 1~2문장",
 "evidence_ai": ["AI 생성 쪽을 가리키는 근거, 각 한 문장. 없으면 빈 배열"],
 "evidence_real": ["실제 촬영 쪽을 가리키는 근거, 각 한 문장. 없으면 빈 배열"],
 "heatmap_focus_detailed": "히트맵과 크롭이 짚은 곳에 실제로 무엇이 보이는지 2~3문장",
 "heatmap_useful": "yes | partial | no",
 "heatmap_comment": "히트맵이 판정 근거를 제대로 짚었는지, 엇나갔다면 어디를 봤어야 했는지 1~2문장",
 "reasoning": "양쪽 근거를 저울질해 판정에 이르는 과정 3~4문장",
 "uncertainty": "확신을 깎는 요인 한 문장. 없으면 빈 문자열",
 "explanation_detailed": "최종 설명 8~12문장. 장면 → 근거 → 히트맵 → 결론 순서로 이어 쓴다"}
```

`teacher_verdict`, `teacher_confidence`, `observations`는 배치 파일에서 그대로 복사되므로
출력에 다시 쓰지 않는다. `merge` 단계에서 합쳐진다.
